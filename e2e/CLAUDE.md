# End-to-end tests

Playwright drives the production build in Chromium, Firefox and WebKit. Package name `@skysend/e2e`, versioned on its own like the Workers, so `version:sync` leaves it alone. The long-form guide for people is `docs/developer-guide/reference/testing.md`, keep both in step.

```bash
pnpm test:e2e:install                                  # Browsers, apt libraries on Linux (sudo), Caddy into e2e/.tools
pnpm test:e2e                                          # Builds crypto, note-format, server and web, then runs everything
pnpm test:e2e:ui                                       # Builds, then the Playwright UI at http://localhost:9323
pnpm test:e2e:large                                    # Builds, then only large.spec.ts with a file of 5 GiB
```

The UI is served as a page instead of a window, so it works on a machine without a display. Its Service Worker needs a secure context: it only renders through `localhost`, an IP address or hostname shows a black page. It starts with the Chromium project selected.

`pnpm test` and `pnpm validate` do not run these. CI runs them in the **E2E Tests** job of `validate.yml`.

## How a run is wired

- `scripts/serve.mjs` wipes `DATA_DIR`, imports `apps/server/dist/index.js` and puts a recording proxy in front of it, on `PROXY_PORT` with the server one port above. `BASE_URL` is the origin the browser opens, so CORS and the WebSocket origin check pass. The proxy copies the server's connection timeouts (keep-alive 120 s), so Caddy and Nginx meet the same backend they would meet without it.
- `TARGETS` in `playwright.config.ts` starts one such server per setup, each with its own `skysend-e2e-<name>` data directory in the temp folder. Ports: `direct` 3170, `caddy` 3443 with recording proxy 3270, `caddy-chunks` 3444 and 3370, `nginx` 3445 and 3470, `nginx-chunks` 3446 and 3570, the config variants 3610 to 3650, snapshots from 3700 in steps of 10. Proxy files live in `<tmpdir>/skysend-e2e-proxy-<name>`, apart from the data directories the servers wipe. Projects are `<engine>` for direct and `<engine>-<setup>` for the rest.
- `s3` (3660, store 3668) runs files and requests in Chromium and WebKit against SeaweedFS from `scripts/s3.mjs`, which creates the bucket before the server's `HeadBucket` at startup. The project option `storage` is `s3` there, and the file and request round trips check with `watchPresigned` that the download came from the bucket, or on a filesystem that it never did. `oidc` (3680, provider 3688) runs `scripts/oidc.mjs`, oidc-provider with its development login form over HTTPS with a self-signed certificate. openid-client refuses an HTTP issuer, so that one server gets `NODE_TLS_REJECT_UNAUTHORIZED=0`, no other. Services start before the servers, and Playwright starts web servers in order.
- `scripts/container.mjs` runs the Docker services, removing a left-over container of the same name first and the container on SIGTERM. Give every new container entry `gracefulShutdown`, Playwright kills web servers outright otherwise and the container outlives it. `quiet` drops a chatty log, SeaweedFS runs with `-master.telemetry=false`.
- `cli.spec.ts` and `cli-requests.spec.ts` run the built `apps/client/dist/index.js` (`test:e2e:build` builds it) with `--json` and `HOME` and `XDG_CONFIG_HOME` in the test's output folder, through `support/cli.ts`. `E2E_CLI=binary` runs the Bun binary `apps/client/dist/skysend` of `pnpm client:compile` instead, run that before a change to the CLI is done. Its tests that need one browser only skip the others. `note:view` is the TUI, so a note is only read the other way.
- The CLI's OIDC login is tested in `config.spec.ts` under `[oidc]`: `cliWithLogin` puts a stand-in `xdg-open` that opens nothing on the PATH, reads the login address the CLI prints, and the page logs in there, after which the server sends the session to the CLI on 127.0.0.1. Linux only, because of that stand-in. The test asserts the upload went over the WebSocket, without the token in the handshake it falls back to HTTP and fails.
- Which tests run where: `direct` runs every spec but `compat.spec.ts` and `config.spec.ts`. A target with `testMatch` runs only those specs, the proxies the `WIRE` list (files, requests, links, transport) plus notes behind Caddy and the guard where there is a WebSocket, in Chromium and Firefox only (`PROXY_ENGINES`). WebKit on Linux speaks HTTP/2 and TLS through libsoup, a network stack no Safari has, so behind a proxy it tested nothing a user runs, while it doubled the slowest CI job. WebKit stays in the direct setup, with S3 and with the snapshots, where its Blob download path and the app itself are what counts. Do not put it back behind a proxy. A target with a `tag` picks its tests out of a shared spec by `[tag]` in the title, through `grep`: the snapshots in `compat.spec.ts`, and the server settings of `variant()` in `config.spec.ts`, which run in Chromium only. A new server setting to test is a new `variant()` and a `[name]` block, not a branch in a test. App logic goes into a spec that runs on `direct` only, never into `WIRE`.
- The **Changes** job of `validate.yml` skips the E2E jobs of a pull request into `dev` whose files miss its `PATHS` pattern (`apps/`, `packages/`, `e2e/`, the root package files, the reverse proxy guide, `validate.yml`), with `CLAUDE.md` files left out. When the tests start to depend on another path, add it there, or such a change skips the tests that would have caught it.
- `E2E_BROWSER` (one engine or a comma list) narrows every target to those engines and drops a target left with none, together with its web servers, proxies and containers, and the tool checks only cover what is left. CI runs a matrix job per engine on it.
- CI time is the budget. The user wants the E2E jobs about as long as the rest of Validate, which takes a minute, while the image build takes two. The first run on GitHub (2026-10-11) took 5:18 for Chromium, 6:06 for Firefox and 10:19 for WebKit before WebKit left the proxies, almost all of it in the tests, not the install. A runner has 4 cores, the config gives CI 3 workers, and WebKit runs about twice as slow there as on skydev. Before a new spec goes into every engine and setup, ask which engine and which setup it adds something in, and run it only there, like `variant()` and the CLI tests do.
- No web server is ever reused (`reuseExistingServer: false`). One left from a UI mode would serve its old configuration, which once made every expiry test fail against a server without the 5 second option. `E2E_PORT_OFFSET=1000` shifts every port, data directory and Nginx container, so a run goes beside an open UI mode.
- `proxies/Caddyfile` keeps each site to the bare `reverse_proxy` line of the published docs. The global block only keeps Caddy local: its own CA, `skip_install_trust`, storage in the temp folder, bound to 127.0.0.1, no port 80 redirect, HTTP/3 off so the protocol does not depend on timing.
- `scripts/install-caddy.mjs` pins Caddy's version and the SHA-512 of each archive. Raising the version means new hashes from the release's checksums file. Without the binary, a local run drops the Caddy targets with a warning and CI throws.
- `scripts/images.mjs` holds the Docker images of the services, pinned by digest, and `nginx.mjs` and `s3.mjs` import them from there. Run directly, it pulls the named ones side by side, which each CI job starts in the background before it installs, with the images of its browser from the matrix of `validate.yml` (`nginx` behind Chromium and Firefox, `s3` behind Chromium and WebKit). A new service image or a setup that moves to other engines needs that matrix updated too. A missing entry only costs the head start, the service pulls its image itself.
- `scripts/nginx.mjs <name> <port> <upstream>` reads the `nginx` block of `docs/user-guide/self-hosting/reverse-proxy.md` on every start, drops the port 80 redirect and replaces the `listen`, the two certificate lines and `proxy_pass`, each of which has to match exactly once. A reworded example fails there on purpose, adjust the patterns with the docs. It runs `nginx:1.30.5-alpine` pinned by digest with `--network host` and a fresh self-signed certificate, and removes the container on SIGTERM. Without a working `docker info`, a local run drops the Nginx targets and CI throws.
- Known flake, as of 2026-10: WebKit on Linux sometimes never answers the very first navigation of a fresh context, over HTTPS and over plain HTTP alike, about once in 300 tests and only in full runs under load. Nothing reaches the proxy or the server, Chromium and Firefox never do it, and Safari's network stack is a different one. CI retries once, so it shows as flaky. Do not paper over it with a navigation retry in the helpers.
- Nginx 1.25.1 and later warn that `listen ... http2` from the docs is deprecated. The docs keep it on purpose: `http2 on;` breaks the Nginx 1.24 of Ubuntu 24.04 and older.
- Chromium refuses a Service Worker from an origin with a certificate error even with `ignoreHTTPSErrors`, and falls through to the file picker, which hangs. The Chromium projects behind Caddy launch with `--ignore-certificate-errors` for that.
- The proxy records every request line, header, body and unmasked client WebSocket frame, and answers `POST /__e2e__/scan` with the needles it finds. It strips `Sec-WebSocket-Extensions` so frames stay uncompressed.
- The recording sits on the server side on purpose. Playwright misses Service Worker requests in Firefox and WebSocket frames in WebKit, so a check built on `page.on("request")` passes where a leak happened.
- `CLEANUP_INTERVAL` is a day, so a share that ran out shows "limit reached" instead of vanishing mid-test. The rate limit, the quota and the daily request limit are lifted, since every test comes from one address.

## Writing tests

- Import `test` and `expect` from `./support/fixtures.js`. Its `guard` fixture is automatic and fails a test when any needle reached the server.
- Feed the guard everything secret: `guard.secretOf(link)` (base64url, base64, hex and raw bytes of the key), `guard.text(...)`, `guard.content(name, data)`. Content under 32 bytes is skipped, a one-byte needle matches everywhere.
- A file request has two links. `guard.requestLinks(uploadLink, inboxLink)` adds both fragments and, decoded with the real decoders of `@skysend/crypto`, the link secret and the inbox secret on their own. The public key of the upload link is no secret and stays out.
- File request flows live in `support/requests.ts`. Uploads sent together sit in a nested list, so `inboxRow` picks the innermost list item.
- Generate data with `randomFile`, `randomText`, `randomPassword` from `support/flows.ts`. A fixed string could appear by chance.
- The recipient is `openRecipient()`, a fresh context. Never reuse the sender's page, its IndexedDB holds the link.
- A test that moves a large file calls `test.slow()`, which triples its 60 seconds. The 32 MB chunk test ran out of time in WebKit on a CI runner once, a minute is too short for 32 MB up and down and a decryption in memory with other tests beside it.
- Every download goes through `watchTiers(page)` and asserts `expect(tiers).toEqual([expectedTier])`: tier 1 in Chromium and Firefox, tier 4 in WebKit, whose OPFS on Linux reads back an empty file, so Safari's tier 3 only gets tested on a Mac and through `service-worker.spec.ts` in Firefox with Service Workers blocked. A broken tier falls through and the file still arrives, only this assertion notices.
- The automatic `uploadTransports` fixture collects the transport the upload worker logs in every context of a test, including recipients, and fails when one differs from the target's `uploadTransport` option. `transport.spec.ts` asserts the protocol (`nextHopProtocol`) and that an upload logs a transport at all.
- The app has no test ids. Select by role and the English label (`locale: "en-US"`). The option pills open a `radiogroup`, not a `group`.
- A WebSocket the server rejects drops whatever the browser had not sent yet in WebKit. Send one message per socket when a test needs frames on the wire.
- `page.goto` to the URL the page is already on, fragment included, is a same-document navigation and reloads nothing. A second visit to the same link, like a sender after "Delivered", needs a fresh `openRecipient()`, which is also what a second visitor really is.
- A label can collide with a block of the same name: a template field called "Password" shares its name with the Password block's region. `sendToRequest` fills fields by their textbox for that reason, and test data uses distinct labels.
- `rowMenu(row, item)` opens "More actions" of a row in My Links, an inbox or the template list, `confirm(page, action)` presses the button of the dialog that asks first.
- Under Playwright, Firefox takes a folder through the `webkitdirectory` input but never answers the click after it, so the folder test of `archive.spec.ts` skips Firefox. WebKit is the engine it is for, since WebKit drops the path of a File it posts to a worker.
- Firefox shortens the idle timeout of Service Workers through `firefoxUserPrefs` (`dom.serviceWorkers.idle_timeout`), so `service-worker.spec.ts` launches a Firefox of its own with one second to check a download after the worker was stopped. Chromium has no such switch.
- Cancelling a download is not covered: nothing slows a download down reliably, and in Firefox the Service Worker fetches past Playwright.

## Crafted notes and large files

- `crafted-note.spec.ts` sends markup that would run code, load something or restyle the page through every block type and checks the rendered `main` itself: no `script`, `iframe`, `object`, `embed`, `style`, `link`, `meta`, `base`, `math` or SVG other than the app's own lucide icons, no `on…` attribute, no `javascript:`, `data:` or `vbscript:` URL. Checking only that nothing ran is not enough, since the CSP blocks most of it even when the sanitizer fails. `apps/web/tests/components/NoteBlocks.test.tsx` covers the breadth of payloads in jsdom, this one the parsers of the real engines. Both caught a raw HTML hole planted in the plain text block.
- `large.spec.ts` runs only with `E2E_LARGE=1`, which `pnpm test:e2e:large` sets and which runs it alone, in the `large` setup: Nginx with TLS and HTTP/2, Chromium only, `FILE_MAX_SIZE=8GB`, no trace and no video, and `RECORD_BODIES=false` on the recording proxy. `scanServer` refuses a needle marked `inBody`, like `guard.content`, when the setup records no bodies, so a content check never passes for not having looked. Keys and names are still checked in URLs and headers.
- The file comes from xorshift32 per block of a MiB, hashed while it is written, and goes before the download, so the peak is the ciphertext on the server and the download, about 11 GB. The test checks for 2.2 times the size of free disk before it writes, so a full disk fails in a second with a message instead of halfway. Nothing of it goes to the temp folder, which is a tmpfs in memory on skydev and other Linux systems: the source lands in `test-results/`, the server's `DATA_DIR` and Chromium's `downloadsPath` in `e2e/.large-files/`, which is ignored. Measured on skydev: 10 GB at the peak on the disk, 1 MiB in `/tmp`. With `WIPE_ON_EXIT=true` the server of the setup gets SIGTERM instead of a kill and removes its data directory when it exits, and `download.delete()` removes the download, so a finished run leaves only empty folders. `E2E_LARGE_SIZE` (bytes) tries a smaller file first. The CI job **E2E Large File** removes unused toolchains in the background for room and never uploads the `.bin` with a failed report.

## Benchmark

`bench/` measures transfers, it tests nothing and runs in no CI job. `bench/README.md` lists every option, the "Measuring uploads and downloads" section of the testing guide is the version for people.

- `transfer.mjs` (`pnpm --filter @skysend/e2e bench`) runs the built server itself, not through `serve.mjs`, behind two counting TCP relays: A between browser and server, B between server and bucket, and since the presigned URLs point at B, also between browser and bucket on a download. It records the progress the upload worker posts by wrapping `Worker` in an init script and keeping only the progress fields, never a whole message, since `done` carries the secret.
- Chromium runs as the full browser (`channel: "chromium"`), not the headless shell, because behaviour differs where it matters here. The contexts are incognito ones, which keep blobs in memory only, so a result about blob memory needs `pipeline.mjs --persistent` to say what a normal profile does.
- Everything goes to `e2e/.large-files/bench/`, on the disk of the checkout. Never the temp folder, a tmpfs on skydev, where a filesystem upload would measure memory instead of a disk.
- `shape.sh` puts `tc netem` on `lo` with filters on the bench ports only. Always `clear` it afterwards, it outlives the run.
- A run that measures speed needs the machine to itself. Two runs side by side, or a build beside one, change the numbers.

## Snapshots of releases

`compat/snapshots/<version>/` holds `data.tar.gz` (the `data/` and `uploads/` of a server of that release, `data/tmp` left out) and `links.json` (what was shared). Every snapshot becomes a target `compat-<version>` on port 3670 plus 100 per version, whose projects run only `compat.spec.ts` and pick their release's tests by the `[version]` in the title through `grep`.

- `compat/seed.mjs <version>` (`pnpm --filter @skysend/e2e compat:seed`) runs the published `ghcr.io/skyfay/skysend:<version>` with Docker as the current user, shares through its UI with `seed/<version>.spec.ts` or `seed/release.spec.ts`, stops it with SIGTERM so SQLite checkpoints, and packs the result. Make a snapshot once, right after its release, and commit it. Seeding again replaces every key, so never reseed an existing version without a reason.
- `release.spec.ts` uses the current helpers, which fit the release just made. A release with an older UI needs its own seed. Version-specific seeds may break later as the helpers move on, which is fine, they ran once.
- The seed server gets high limits (1000 downloads, unlimited views, 1000 uploads and 100 downloads per request, the most v3.0.1 accepts), since all three engines and their retries share one copy of the snapshot. Inbox and file tests find rows by name, never by count, because the open-request test adds uploads.
- `scripts/serve.mjs` restores a snapshot when `SNAPSHOT` is set: unpacks it, points `DATA_DIR` and `UPLOADS_DIR` at it, and sets every `expires_at` and `closes_at` column of every table a year ahead (seconds or milliseconds, by size) before the server starts and migrates. That works on any schema, so a new snapshot needs no code there. `storage_path` holds `<id>.bin`, relative, so the uploads can move.
- `links.json` keeps path and fragment only, the origin differs per run. File contents come from `compatBytes(file)`, a SHA-256 stream of the file's seed.
- A snapshot made right after its release has the same migrations as the current server. Migrations only get exercised once the schema moves on, or by a snapshot of an older release.

## Checking a check

A new assertion is only worth something if it can fail. Break the thing it guards once and put it back: move `apps/web/dist/download-sw.js` away, which must fail the tier assertion, or give a Caddy site a `request_body { max_size 1MB }`, which must fail the uploads of `caddy-chunks`, or let `extendExpiries` in `scripts/serve.mjs` move the dates a minute into the past, which must fail every compat test.
